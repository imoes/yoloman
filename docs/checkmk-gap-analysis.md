# Checkmk feature gap analysis

Systematic comparison of **Checkmk as the functional reference** against yolo-man, read from the
Checkmk source tree at `../checkmk` (2026-07-01, `4900505af56`) plus the official documentation.

Process, same as [zabbix-gap-analysis.md](zabbix-gap-analysis.md): read an area → extract every
distinct feature → check it against the real codebase (file:line, not memory) → present the gaps →
user decides (implement now / defer / reject) → record the decision here → commit.

Status legend: ✅ implemented · 🟡 partial · ❌ missing · ⏭ out of scope (decided)

**The two references are deliberately split:** Checkmk is the *functional* reference, PostgreSQL +
TimescaleDB the *technical* one. Checkmk's persistence — autochecks files, RRD, config files,
`/omd` — is explicitly **not** adopted; only its logic is. Every such deviation is recorded in the
"Deviation" column or a dedicated note, per the project rule that deviations must be documented.

## Batch 1 — Service Discovery

Read: `packages/cmk-check-engine/cmk/checkengine/discovery/` in full — `types.py`,
`plugins/_discovery.py`, `_discover/services.py`, `_discover/host_labels.py`, `_autochecks.py`,
`_autodiscovery.py`, `_entrypoints/active_check.py`, `_utils/filters.py` — plus
`packages/cmk-plugins/cmk/plugins/lib/interfaces.py` as a worked example of discovery defaults.

**Checkmk's central architecture, in two sentences.** Discovery answers *which objects exist* and
persists that as **autochecks**: `AutocheckEntry(check_plugin_name, item, parameters,
service_labels)` with `id() = ServiceID(plugin, item)` and `comparator() = (parameters,
service_labels)` (`plugins/_discovery.py:27`). Rules answer *how they are monitored*, and are a
separate, human-owned artifact. Every discovery run then compares the persisted set against the
freshly found one through `QualifiedDiscovery` (`types.py:138`), which classifies each service as
`new` / `unchanged` / `changed` / `vanished`.

That comparison is the piece everything else hangs off: the discovery check alerts on those
transitions, periodic rediscovery acts on them, and the discovery page presents them.

| Feature (Checkmk) | Detail / source | yolo-man status | Disposition |
|---|---|---|---|
| **D1 — Persisted discovery result with lifecycle** | autochecks per host; `QualifiedDiscovery` (`types.py:138`) classifies new/unchanged/changed/vanished; `id()`/`comparator()` split identity from change | ❌ discovery is transient (`services/discovery.py:137` returns in-memory proposals); only *accepted* results survive, as `CheckAssignment` rows that also carry the monitoring config | **✅ approved → implemented (phase 1)**: own `discovered_services` table + `classify()` port |
| **D2 — Discovery check** | the `Check_MK Discovery` active check turns transitions into a service state, with configurable severity per transition (`_entrypoints/active_check.py:74-88`: `unmonitored`/`vanished`/`changed`, `severity_new_host_labels`) | ❌ nothing notices that a host grew or lost services | **awaiting decision** — high value, cheap once D1 exists: one service per host graded from the reconcile result |
| **D3 — Periodic / automatic rediscovery** | `RediscoveryParameters` (`_utils/filters.py:31`): `activation`, `excluded_time` windows, `group_time`, `mode` flags, per-transition service filters; driven by `_autodiscovery.py` | ❌ `services/scheduler.py` runs only runbook cron jobs; no discovery job type | **awaiting decision** — needs D1; our scheduler already has the cron machinery to extend |
| **D4 — Bulk discovery** | discovery across many hosts in one operation | ❌ `/discover` is single-host; the AI tool (`services/chat_tools.py:273`) is also per host | **awaiting decision** — mostly an endpoint + job over D1/D3 |
| **D5 — Ignored / disabled services** | a persisted decision that a discovered service stays unmonitored, remembered across runs (plus the "disabled services" ruleset) | ❌ not applying a proposal leaves no trace; the next run offers it again | **awaiting decision** — the `ignored` state is already in D1's schema; needs the API verb |
| **D6 — Discovery filters (regex, per transition)** | `ServiceFiltersDedicated` (`_utils/filters.py:20`): white/blacklists for new, vanished, changed-labels, changed-params — service-name regex | ❌ filtering is only the static platform/datasource/runnability gate (`api/checks.py:245`) | **awaiting decision** — pairs with D3 (that is where Checkmk applies them) |
| **D7 — Host labels + service labels** | discovered at section level (`_discover/host_labels.py`) and per service (in the autocheck); host labels go through the *same* `QualifiedDiscovery` | ❌ absent entirely; `service_labels` is half of Checkmk's change comparator, so D1 is incomplete without it | **✅ approved → implemented (phase 1)**: `service_labels` JSONB on `discovered_services`, `host_labels` table, contract extension |
| **D8 — Idempotent apply / reconciliation** | `set_autochecks_for_effective_host` rewrites the host's set and `_deduplicate` keeps one entry per `id()` (`_autochecks.py:207,231`) | ❌ `/discover/apply` (`api/checks.py:341`) inserts unconditionally — repeat calls duplicate rows | **✅ folded into D1** — `reconcile()` is idempotent by construction |
| **D9 — Enforced services** | a rule that makes a service monitored regardless of discovery | ❌ `CheckRule.enforced` (`db/models.py:1196`) is *GPO precedence*, an unrelated meaning of the word | **awaiting decision** — belongs with Batch 2 (rule conditions) |

### Deviations from Checkmk, and why

| Checkmk | Ours | Reason |
|---|---|---|
| autochecks in a per-host file (`AutochecksStore`, `_autochecks.py:54`) | `discovered_services` table | PostgreSQL is the single source of truth; file state is explicitly rejected by the project rules |
| `Item = str \| None` | `item TEXT NOT NULL DEFAULT ''` | `NULL` does not deduplicate in a Postgres `UNIQUE`, so a single-service check could be inserted twice. Our code already uses `item=""` (`services/discovery.py:40`) |
| ordered rulesets, first-match | GPO precedence + parameter merge (`services/gpo.py:46`) | deliberate: the AD/GPO model is what the simpler UI is built on. Decided 2026-07-30; Batch 2 brings the *conditions* up to Checkmk level (tags, labels, regex) without adopting first-match |
| host labels also from rulesets and explicit config | `host_labels.source` ∈ `discovered\|explicit\|ruleset` | same three sources, one table, source recorded per label |

### Decisions (2026-07-30)

Approved and implemented in phase 1: **D1** (own `discovered_services` table, `classify()` as a
port of `QualifiedDiscovery`, idempotent `reconcile()`) and **D7** (service labels on the
discovered service, `host_labels` table, discovery contract extended). **D8** falls out of D1.

Deliberately *not* in phase 1: switching the execution path from "iterate `CheckAssignment`" to
"iterate `discovered_services` where `state='monitored'`, parameters from rules". That is what
completes the separation, but it changes the live poll path and needs its own decision.

**D2–D6 and D9 await your decision.** Recommended order once D1 is in: D2 (discovery check — the
cheapest real win, it makes drift visible), then D5 (ignored, small and removes a daily
annoyance), then D3+D6 together (periodic rediscovery with the filters that belong to it), then
D4 (bulk). D9 with Batch 2.
